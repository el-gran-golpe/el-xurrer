# El Xurrer Agent Instructions

## Purpose
- This repository is a Python monorepo with two apps and one shared package.
- The AI content app handles influencer content workflows: planning, generation, scheduling, Instagram publishing, Fanvue publishing orchestration, Google Drive resource sync, ComfyUI image generation, and LLM routing.
- The Fanvue FastAPI app handles Fanvue OAuth, session handling, media upload orchestration, and post creation.
- Treat this file as the shared source of truth for coding agents. Codex and opencode read `AGENTS.md`; Claude Code reads `CLAUDE.md`, which imports this file.
- Do not commit or push changes unless the user explicitly asks for that in the current task.

## Agent Instructions Maintenance
- Treat stale agent instructions as a repository bug. At the start of each task, read the applicable `AGENTS.md` files for the area being changed.
- Before finishing any task that changes behavior, commands, architecture, workflows, safety rules, dependencies, external integrations, or testing expectations, decide whether root or app-specific `AGENTS.md` needs an update.
- Update `AGENTS.md` in the same change when the new knowledge is durable and useful for future agents. Do not update it for one-off debugging notes, transient failures, or information already captured accurately.
- Prefer updating `AGENTS.md` rather than `CLAUDE.md`; this repo's `CLAUDE.md` files import their matching `AGENTS.md` files.
- In the final response, mention whether agent instructions were updated or why no update was needed.

- `apps/ai-content-pipeline/ai_content_pipeline/jobs/` contains the resumable plan -> generate_image -> schedule DAG (`JobStore`, `Queue`, `GenerationBackend`, job tasks) driven by the `jobs run` command.
- `apps/ai-content-pipeline/ai_content_pipeline/llm/` contains LLM wrappers, routing, classification, prompt utilities, and API error handling.
- `apps/fanvue-fastapi/` contains the Fanvue FastAPI app, tests, README, and app-specific agent instructions.
- `shared/fanvue-api-client/` contains shared Fanvue OAuth, media upload, post creation, and token-store primitives used by both apps.

- `scripts/start_pipeline_with_comfyui.sh` launches ComfyUI (sibling repo) and the pipeline detached via `setsid`. By default it binds ComfyUI's `--listen` to `COMFY_LISTEN_HOST` (`0.0.0.0`, reachable from other machines on the LAN/ZeroTier), separate from `COMFY_HOST` (`127.0.0.1`, used by the wrapper's readiness curl and by the pipeline's own ComfyUI client since both run on this same machine). Override `COMFY_LISTEN_HOST` to restrict binding, or `COMFY_HOST` to point the pipeline at a ComfyUI instance running elsewhere.
- `Dockerfile` + `docker-compose.yml` (service `pipeline`) run the AI content CLI in a container: image entrypoint is `python apps/ai-content-pipeline/main.py`, compose default command `jobs run` (`docker compose run --rm pipeline <command>`). Nothing stateful or secret is baked in (`.dockerignore` is a whitelist of `pyproject.toml`, `uv.lock`, `apps/`, `shared/`, minus tests/outputs/tokens): `.env` is both injected with `env_file` and bind-mounted read-only at `/app/.env` (required: `Settings.get_meta_credentials`/`get_fanvue_credentials` read per-profile keys from pydantic's `model_extra`, which only contains extra keys from the dotenv file, not from environment variables), and `resources/` (override with `RESOURCES_DIR`), `.cache/`, `logs/` and `~/.config/myapp/` (Google Drive `token.json`) are bind mounts under `/app` / `/home/app`, so paths resolve exactly as on the host and the Drive default-root guard still matches. The image runs as a non-root user whose UID/GID default to 1000 (`APP_UID`/`APP_GID` build args) so mounted files keep the host owner. ComfyUI is not in the stack: compose sets `COMFY_HOST` from `DOCKER_COMFY_HOST` (default `host.docker.internal`, + `host-gateway`; on a deployment machine without a GPU, set it in `.env` to the GPU machine's ZeroTier IP), never from `${COMFY_HOST}`, because Compose also reads `.env` for `${...}` interpolation and a host-side `COMFY_HOST=127.0.0.1` would point the container at itself. `TZ` is set because `planning_week_start(date.today())` and naive `upload_time`s depend on local time. Browser-based auth (`fanvue auth`, first Drive authorization) cannot run in the container; do it on the host. Keep `python3.12` in the base image aligned with the local `.venv`, and update the image/compose when adding new runtime paths or env-driven settings.
- To start ComfyUI on its own (e.g. before `jobs run`): it lives in the sibling repo `../ComfyUI` (next to `el-xurrer/`), launched from there with `uv run main.py --listen 0.0.0.0` (port 8188 by default). Check it is up with `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8188/` (expect `200`). Starting it is a side effect on the user's machine (GPU, LAN-reachable listener), so ask before launching it; run it in the background and stop it when done if you started it.

- Keep environment setup centralized in the repository-root `.env` and `.env.example`; do not add app-local copies. The AI content CLI resolves `.env` relative to the current working directory, so launch it from the repository root (including IDE configurations). Fanvue FastAPI uses an absolute repository-root `.env` path.

## Commands
- Install/sync dependencies: `uv sync`
- Run Ruff formatting: `uv run ruff format .`
- Check Ruff formatting: `uv run ruff format --check .`
- Run Ruff linting: `uv run ruff check .`
- Run mypy: `uv run mypy`
- Run all tests: `uv run pytest -q`
- Run all configured checks: `uv run pre-commit run --all-files`
- Run the AI content CLI: `uv run python apps/ai-content-pipeline/main.py --help`
- Run Fanvue FastAPI locally only when needed: `uv run python apps/fanvue-fastapi/main.py`
- Run the full AI content pipeline for all loaded profiles: `uv run python apps/ai-content-pipeline/main.py all run_all`
- Every CLI command with profile selectors defaults to all loaded profiles when neither `-p/--profile-indexes` nor `-n/--profile-names` is passed. This includes `all run_all`, `all debug`, Meta/Fanvue `plan`, `generate`, and `schedule`, and `fanvue auth`.
- Explicit selectors limit the run: repeat `-p` for multiple indexes or pass comma-separated names with `-n`. Indexes take precedence when both selectors are provided. Invalid explicit selections, including an empty `-n ""`, must never fall back to all profiles. Keep this behavior centralized in `resolve_profiles()`.
- PyCharm's general and all-profile CLI configurations omit profile selectors; configurations explicitly named for a particular profile keep their selector. Use `all run_all` for normal runs and `all debug` for debug runs. The "No overwrite" configuration needs both `--no-overwrite-outputs` and `--keep-local-outputs` to preserve existing planning files at startup.
- `all run_all` clears each selected profile's Meta and Fanvue `outputs/` folders before planning/generation by default. Pass `--keep-local-outputs` only when intentionally reusing existing outputs.
- Run the resumable DAG equivalent of `all run_all`: `uv run python apps/ai-content-pipeline/main.py jobs run`. Add `--skip-schedule` to exercise plan/generate/resume without publishing to Meta/Fanvue or sleeping until `upload_time`. Add `--weeks N` (default 1, minimum 1) to plan N consecutive weeks per profile+platform in one run instead of only today's target week.
- Report on a `jobs run` without re-running anything: `uv run python apps/ai-content-pipeline/main.py jobs status`. Read-only (no Drive pull, no profile loading, no LLM/ComfyUI/network): shows the last run's summary plus a per profile/platform/week overview of current story/plan/images/schedule state. `--run <id>` shows a specific run, `--runs` lists recent runs with their failure counts.
- Generate the season-level story arc covering a week, on its own: `uv run python apps/ai-content-pipeline/main.py arc plan`. `--week YYYY-MM-DD` defaults to this run's target week (`planning_week_start(today)`); an existing arc covering that week is reused unless `--force`. `jobs run` also does this automatically as part of its "story" step — see Jobs DAG.
- Generate the chapter covering a week, on its own: `uv run python apps/ai-content-pipeline/main.py chapter plan`. Same `--week`/`--force` options; ensures the covering arc exists first (never forced) before generating the chapter.

## Jobs DAG
- `docs/story-dag.md` diagrams the story -> plan flow below (arc, chapter, angle refresh, plan fingerprint, frozen weeks, retries) as a Mermaid flowchart. Update it in the same change whenever those conditions change.
- `jobs run` is the resumable alternative to `all run_all`: node state lives in SQLite at `JOBS_DB_PATH` (default `.cache/jobs/state.db`, outside `resources/`), so re-running the same command after a crash or Ctrl+C skips nodes already `done`.
- Unlike `all run_all`, `jobs run` never clears `outputs/`. Generated images are part of the checkpoint; deleting them means regenerating them.
- `all run_all`, `all.py`, and `pipeline.py` stay as the fallback path until the DAG is validated in real use. Do not delete or rewrite them as part of DAG work; keep both paths working.
- The DAG sits behind three small interfaces so a future Redis/RQ queue or an HPC (SLURM) generation backend is an implementation swap, not a rewrite: `JobStore` (node state, `params_hash` invalidation, fan-in counter), `Queue` (per-type asyncio queues with their own worker pools), `GenerationBackend` (`generate(spec, output_path)`, contract: the file exists when it returns).
- Concurrency per job type is decided by whoever registers the handler (`cli/commands/jobs.py:register_handlers`), not by `Queue`: `story` and `plan` are both 1 because each builds its own `ModelRouter`, whose key cursor is not concurrency-safe, `generate_image` is 1 because it is one local GPU, `schedule` gets one worker per job because Meta scheduling sleeps until each `upload_time`. `--weeks N` week ordering does not rely on `story`'s concurrency=1 being FIFO — see below, it is enforced by explicit DAG edges instead.
- `LocalComfyBackend.generate` bridges to the blocking `ComfyLocal` with `asyncio.to_thread`. That is deliberate but temporary: calling it directly would freeze the event loop and head-of-line block the `plan` and `schedule` queues. The real fix is making `integrations/comfyui/local.py` async (`httpx.AsyncClient` + an async websocket client), after which the `to_thread` goes away and nothing else in the DAG changes.
- `jobs run --skip-schedule` also skips the per-profile Meta Page-token validation that normally runs before the DAG starts: nothing is published, so there is nothing to validate against.
- The week a `plan` job targets is the ISO date of a Monday (e.g. `"2026-10-12"`), computed once per `jobs run` invocation by `planning_week_start(date.today())` (`llm/utils/utils.py`): today if today is a Monday, otherwise the next Monday. It is deliberately a pure function of the clock, never "the Monday after the latest planned week" — that rule would plan a new week on every re-run and break resume. `seed_story` computes it once and passes the same value to every profile's `story` job in that run (which in turn passes it to every platform's `plan` job), so the run cannot straddle midnight into two different target weeks. `PlanningManager` overwrites the LLM's reply's top-level key with this target week regardless of what the model used (the prompt JSONs under `resources*/` still say the literal `"week_1"`; only the saved file's key changes). `WeekPlan.pin_to_week` then enforces one publication day per calendar day: the plan must be exactly days 1-7 with at least one post each (otherwise `ValueError`, so the `plan` job fails and re-plans next run), and day N's `upload_time` is rewritten to `week_start + (N - 1)` keeping the model's time of day (18:00 UTC if unparseable; naive times are read as UTC). `plan_job_id` includes the week (`plan:{profile}:{platform}:{week}`), so each week gets its own resumable job; `schedule_job_id` also includes the week (see below).
- `PlanningManager._generate_valid_plan` retries the generate -> parse -> override week key -> pin sequence per profile+platform up to `MAX_PLAN_ATTEMPTS = 5` times via the shared `llm/retry.py:generate_with_retries` helper (see the `StoryManager` bullet below for what that helper does): excludes the model that produced an invalid reply before each retry, and routes the last attempt to the paid fallback only. Nothing is saved until an attempt succeeds; if every attempt fails, `PlanningFailedError` propagates and the `plan` job is marked `failed`.
- **Arc -> chapter -> plan** (`domain/story.py`, `planning/story_manager.py`): three levels, each depending only on the one above. `Arc` (free, platform-blind: `title`/`premise`/`goal`/`conflict`/`starting_point`/`ending_point`/`summary` over `weeks` weeks from `start_week`, an ISO Monday) is the season's intention. `Chapter` tiles a slice of the arc (`weeks` consecutive weeks from `start_week`, validated to be exactly `weeks * 7` contiguous `ChapterDay`s) into day-by-day beats: each `ChapterDay` has a neutral `situation` (safe for every platform) plus one `angle` per `Platform.value` (`meta`/`fanvue`) on how that platform lives the day. `Chapter.week_slice(week)` returns one week's 7 days. `StoryConfig` (`story/config.json`, defaults 12/4 if missing) holds `arc_weeks`/`chapter_weeks` per profile; `chapter_weeks` must be `<= arc_weeks`. Both are generated with `is_sensitive_content=True` (the arc may be adult; the chapter prompt additionally requires `situation` and the `meta` angle to stay safe for work, enforced by instruction since Meta reads them through `plan`). `domain/story.py:determine_new_arc_start`/`chapter_boundaries_for_week` are the pure tiling rules: a new arc starts the Monday after the previous arc ends (or at the requested week with no previous arc); chapters tile the arc in `chapter_weeks`-sized chunks from `arc.start_week`, with the last chapter shorter when `arc_weeks` is not a multiple of `chapter_weeks`.
- `FilesystemProfileRepository` stores arcs/chapters at `resources/{profile}/story/arcs/{start_week}.json` / `story/chapters/{start_week}.json` (resolved from `resource_path`/`profile.name`, same as `persona.md` — never from `PlatformInfo`), one file per arc/chapter start week, user-editable. `get_arc_covering`/`get_chapter_covering(profile, week)` scan for the one whose `[start_week, end_week]` contains `week`; `get_previous_arc(profile, before)` finds the latest arc starting strictly before `before`; `get_chapters_of_arc(profile, arc_start_week)` lists one arc's chapters.
- `StoryManager` (`planning/story_manager.py`) generates arcs/chapters the same way `PlanningManager` generates plans: its own `ModelRouter`, the shared `llm/retry.py:generate_with_retries` helper (model exclusion after an invalid attempt, last-attempt-on-fallback — `PlanningManager._generate_valid_plan` now calls the same helper, so the retry policy lives in exactly one place), `is_sensitive_content=True` prompts built in code (not per-profile files). `ensure_arc`/`ensure_chapter(week, force=False)` reuse an existing covering file unless `force=True` — arcs/chapters are hand-edited, so "it's on disk" always wins over "the inputs changed", unlike `plan`'s hash-based resume. The arc prompt reads the persona + **every** platform's notes + the previous arc's summary (+ its chapters' summaries); the chapter prompt reads the arc + persona + every platform's notes + the previous chapters of the same arc (summaries + last week's situations).
- **Hand edits to a chapter** (`ChapterDay.stamp`, `StoryManager.sync_hand_edits`): each `ChapterDay` carries a `stamp` — short hashes of its `situation` and `angles` as last written together (by `plan_chapter`, or accepted after a hand edit; `None` on days written before stamps existed). The angles are derived from the situation, never the reverse, so whenever `ensure_chapter` reuses an existing chapter it reconciles it: a day whose situation changed but whose angles did not (`angles_are_stale`) gets its angles regenerated from the new situation (one `generate_with_retries` call for all such days of the chapter, `chapter_angles_refresh`, same 5-attempt policy); a day whose angles were edited too, or that has no stamp, is accepted and re-stamped; a day in a week that has already started (Monday <= today) is left alone with a warning, same reasoning as frozen `plan` weeks. The chapter is saved only if something changed. This exists because a real run showed both platforms' plans following a stale angle (Fanvue entirely, Meta half) after only the situation was hand-edited. A failed regeneration raises `StoryGenerationFailedError`, so in the DAG the `story` job fails and blocks that week like any other story failure.
- Angles are written as directions, not posts (`_ANGLE_GUIDANCE` in `story_manager.py`, shared by the chapter week prompt and the angle refresh prompt): third person, one or two sentences, inside the situation, no first person/hashtags/caption text — angles written as finished captions were being copied verbatim by `plan`. `build_previous_storyline` labels each day as `Situation: ... | Angle (direction only): ...` for the same reason.
- `StoryManager.plan_chapter` generates a chapter as an outline call plus one call per week, never the whole chapter in one reply: a real run asked a model for a whole 4-week (28-day) chapter and got 7 days back (`Chapter`'s own "Expected 28 days ... got 7" validation caught it, but nothing retried at the right granularity). The outline call produces a `ChapterOutline` (`title`/`summary`/`week_summaries`, one short summary per week — `plan_chapter` rejects a reply whose `week_summaries` count does not match `weeks` before any week call is made). Each week call then produces exactly that week's 7 `ChapterDay`s as a `ChapterWeekDays` (validated to be exactly 7 entries), reading the arc/persona/platform-notes context, the chapter outline, the previous chapters' context (as before), and the `ChapterDay`s already generated for this chapter's own earlier weeks (for continuity within the chapter) — built by `_build_chapter_week_storyline`. All calls for one chapter share a single `ModelRouter` (so an exclusion from one call still applies to a later one) but each has its own `generate_with_retries` budget (`MAX_CHAPTER_ATTEMPTS`, independently per call). `ChapterOutline`/`ChapterWeekDays` (`domain/story.py`) are wire-only shapes for these replies, never persisted; only the assembled `Chapter` is validated as a whole (`Chapter.model_validate`, validators unchanged) and saved, and only after the outline and every week succeeded — a `GenerationFailedError` from any call aborts the whole chapter before anything is assembled, so a failure partway through (e.g. week 2 of 4 exhausts its attempts) leaves nothing on disk, same guarantee a single-call failure used to give. `ChapterOutcome` aggregates the per-call outcomes: `attempt` is the worst attempt number any call needed, `used_fallback` is true if any call needed the paid fallback, `model`/`invalid_attempts` reflect the latest/every call. Progress is logged per week: `Chapter for {profile} {start}: week {i}/{n} generated`.
- `PlanningManager.plan()` calls `self._ensure_story(profile, week_key)` for each profile before building the storyline: it constructs a `StoryManager` and calls `ensure_arc`/`ensure_chapter` (never `force=True`) so `plan` depending on a chapter cannot break the non-DAG fallback path (`meta plan`, `fanvue plan`, `all run_all`/`pipeline.py`), which has no "story" DAG node guaranteeing one exists first. In `jobs run`, the story job already secured both, so this is a cheap no-op there: `ensure_arc`/`ensure_chapter` check the repository (`get_arc_covering`/`get_chapter_covering`) before building any `ModelRouter` or calling the LLM (the only exception is `sync_hand_edits` finding stale angles, which the story job already reconciled first), so the DAG `plan` path builds no extra router and makes no extra LLM call. `_ensure_story` never touches `JobStore`: `PlanningManager.plan()` runs inside `asyncio.to_thread` in the DAG (`jobs/tasks.py:run_plan`), and `JobStore`'s sqlite3 connection is not thread-safe.
- `planning/planning_manager.py:build_previous_storyline` is the isolation boundary: for platform P and week W it assembles persona + P's own `initial_conditions.md` (if `use_initial_conditions`) + P's slice of the chapter covering W (date, `situation`, and **only** `angles[P.value]` for each of the 7 days, via `Chapter.week_slice`). It never reads the arc, the other platform's angle, or the other platform's notes — Meta's call cannot see Fanvue's, and vice versa, enforced in code, not just by prompt instruction. Raises `ValueError` if no chapter covers W — by the time this runs, `_ensure_story` (above) has already guaranteed one, in the DAG or not, so this should never actually happen; it is a clear signal when `build_previous_storyline` is read directly (e.g. `jobs/tasks.py:run_plan`'s hash computation) against a repository that skipped `_ensure_story`. This replaced the old per-platform `## Last week` recap (`get_previous_week_plan`/`summarize_week`, both removed): continuity is now the chapter's job, shared by both platforms, not a platform-own weekly recap.
- `jobs/tasks.py:run_plan`'s resume hash is computed over exactly what the prompt gets: the validated prompts JSON, the full `previous_storyline` (now including the chapter's week slice), and the target week — built with the same `build_previous_storyline` call `PlanningManager` uses, so the hash can never drift from what is actually sent to the LLM. Editing the chapter's slice for that week, or the persona/`initial_conditions.md`, correctly triggers a replan; nothing else does — **except** a frozen week (next bullet).
- **Frozen weeks:** a `plan` job already `done` whose week's Monday has arrived (`date.fromisoformat(week) <= date.today()`) is never re-planned, even if its resume hash changed — checked in `run_plan` *before* `store.create()` would otherwise reset it to `pending`. "Frozen" only applies when the hash actually changed; a started week with unchanged inputs takes the normal `plan_reused` path. Logged as `Week {week} for {profile} {platform} is frozen (already started); not re-planning despite changed inputs` and recorded as a `plan_frozen` event.
- A "story" DAG node (`run_story`, `jobs/tasks.py`) sits above `plan`: for one profile+week it ensures the arc and chapter covering that week exist (generating whichever is missing via `StoryManager`), enqueues that week's `plan` job for every platform, and — in a `--weeks N` chain — enqueues week+1's own `story` job. `story_job_id` is `story:{profile}:{week}` (no platform: the arc/chapter is shared, not owned by one platform); `jobs.platform`/`job_events.platform` are nullable to allow this. If ensuring the arc/chapter fails, nothing below it runs for that week (no `plan` jobs, no next-week `story` job), recorded as `story_failed` plus a `week_not_enqueued` event for the next week — the same "a failed step blocks what depends on it" rule `--weeks N` always had, just moved up from `plan` to `story`.
- `jobs run --weeks N` (default 1, Typer-enforced minimum 1) plans N consecutive weeks per profile in one run instead of only today's target week. Week chaining is now the **story** step's job, not `plan`'s: `seed_story` (`cli/commands/jobs.py`) computes `start = planning_week_start(date.today())` once and enqueues only the FIRST week's `story` job per profile, with `StoryJob.remaining_weeks = N - 1`; `run_story` enqueues week k+1's `story` job itself, as an explicit DAG edge, only after week k's arc+chapter are secured and week k's `plan` jobs are enqueued. `ProfileJob` (the `plan`/`schedule` payload) no longer carries `remaining_weeks` — `plan` never chains weeks itself now. A later `jobs run` re-seeds week 1 per profile and the chain resumes from whichever week is not yet done.
- `FilesystemProfileRepository` keeps `{initials}_planning.json` holding only the current week, same as before real week keys. `save_week_plan` archives whatever week was current to `outputs/history/{week}_planning.json` first if the week being saved is different (overwriting an existing history file with a warning) — unless the week being saved is strictly *older* (ISO comparison) than the current week, in which case it is written straight to `outputs/history/{week}_planning.json` and current is left untouched, so a late/retried older week (e.g. after a mid-chain `--weeks N` failure) can never demote a newer week that is already current. A legacy non-dated current always counts as older than any dated week, so that case still archives normally. `get_week_plan(profile, platform, week=None)` returns the current plan by default, or resolves a specific week against current-then-history, raising `FileNotFoundError` if neither has it.
- `PostingScheduler` accepts an optional `weeks: Collection[str] | None = None` to restrict which week folders under `publications/` it reads; `None` (the default, used by `all run_all`/`pipeline.py`) reads every week folder, unchanged from before. `jobs/tasks.py:run_schedule` passes `weeks={payload.week}` so a `schedule` job only publishes the week it was planned for — `jobs run` never clears `outputs/`, so older week folders (including a legacy `week_1`) can still be sitting there with past-due upload times that would otherwise be published again immediately. `_iter_day_folders` accepts both the legacy `week_N` folder name and the real ISO-date week key.
- `schedule_job_id` is `schedule:{profile}:{platform}:{week}` — it gained the week dimension alongside `--weeks N`, so two weeks of the same profile+platform planned in one run get their own `schedule` job, fan-in counter, and resume state instead of one week's completion resetting the other's params hash. Because Meta's `schedule` sleeps until each `upload_time` and must not block another week's `schedule` behind it, whoever computes `schedule`'s worker count (`cli/commands/jobs.py:_execute`) multiplies it by the number of weeks: `max(1, len(profiles) * len(Platform) * weeks)`.
- A re-plan changes image file names (`{slug}_{index}.jpeg` derives from the post title), so `run_plan` (`jobs/tasks.py`) deletes stale images left under the old names: right after an actual (re)plan (never on the "already done" resume path), and before fan-out, it removes every file under `publications/{week}/day_*/` that is not among the new plan's expected output paths (logged as `Removing stale image {path} (week {week} was re-planned)`), leaving `captions.txt`/`upload_times.txt` and other weeks' folders untouched. A re-plan that keeps a post's title (so its file name is unchanged) but changes its `image_description` is a separate case this filename-based cleanup cannot catch: `_fan_out_images` reads the `generate_image` job's previously stored `params_hash` via `JobStore.params_hash(job_id)` *before* `store.create()` overwrites it, and if the hash changed and the old file still exists, deletes it there (logged as `Removing stale image {path} (description changed for the same file name)`) — this matters because `run_generate_image`'s own `output_path.exists()` skip-check has no hash awareness and would otherwise treat the stale file as already done.
- `jobs run` no longer always prints a blanket success line: `Queue._worker` swallows a handler's exception (`logger.exception`, then moves on, so one failed node never kills the whole run), so `cli/commands/jobs.py:run` finds out about failures by looking at what happened, not by whether anything raised up to it. `JobStore` (`jobs/store.py`, `jobs/schema.sql`) has two tables for this, added as `CREATE TABLE IF NOT EXISTS` so an existing DB upgrades in place without touching its `jobs`/`fan_in_counters` data: `runs` (one row per `jobs run` invocation — `run_id`, `started_at`, `finished_at`, `args`, `outcome`) and `job_events` (append-only facts about one DAG node during one run, each a `JobEventKind` — `plan_reused`/`plan_done`/`plan_failed`/`plan_attempt_invalid`/`plan_frozen`/`week_not_enqueued`/`image_generated`/`image_reused`/`image_stale_removed`/`image_failed`/`schedule_done`/`schedule_skipped`/`schedule_failed`/`arc_done`/`arc_reused`/`chapter_done`/`chapter_reused`/`story_failed`). SQLite cannot `ALTER` a `CHECK` constraint, so `JobStore._prepare_schema` upgrades an existing DB whose `jobs`/`job_events` tables predate the `story` type and nullable `platform` (checked by whether `'story'` appears in `sqlite_master`'s stored `CREATE TABLE` text): it renames the outdated table out of the way, lets `schema.sql`'s `CREATE TABLE IF NOT EXISTS` recreate it in the current shape, copies the old rows across, then drops the renamed one — a no-op for a fresh DB or one already current. `register_handlers`/`_execute` create one `run_id` per `jobs run` (`store.start_run`) and thread it through `run_story`, `run_plan`, `run_generate_image`, `run_schedule`, and `handle_schedule`'s `--skip-schedule` branch, which record events at the same points the DAG already logs them (reuse/replan/failure, stale-image removal, fan-in, publish/skip/fail).
- `PlanningManager.plan()` returns a `list[PlanOutcome]` (one per `template_profiles`, almost always one in the DAG) instead of `None` — `attempt`, `max_attempts`, `model` (`"provider/identifier"` from `model_router.last_model`, or `None`), `used_fallback`, `pinned_corrections`, and `invalid_attempts` (every failed attempt's error text). Callers outside the DAG (`cli/commands/pipeline.py`, `all.py`) still just call `.plan()` and ignore the return value. When every attempt fails, `_generate_valid_plan` raises `PlanningFailedError` instead of the bare last error — a `ValueError` subclass (so `except ValueError` and `pytest.raises(ValueError, match=...)` callers keep working unchanged) that carries `invalid_attempts`, so `run_plan` can record a `plan_failed` event with every attempt's error, not just the last one. This is purely additional: the 5-attempt retry, model exclusion, and last-attempt-on-fallback semantics are unchanged.
- `cli/commands/jobs.py:run` builds an end-of-run summary table from `jobs/report.py:build_run_rows(store.events_for_run(run_id))` — one row per profile+platform+week touched by the run, with outcome (planned now / reused / failed / not reached / frozen), a Story column (`arc generated`/`arc reused`/`chapter generated`/`chapter reused`, comma-joined — a `story` event has no platform, so it lands on its own pseudo-row with `platform=""` alongside the per-platform `plan` rows for the same profile+week), planning detail (attempt, model, fallback used, `pin_to_week` corrections) when planned now, image counts (generated/reused/stale removed/failed), and schedule status (published/skipped/failed/not reached). A `week_not_enqueued` event (from a failed `plan` or a failed `story`) is rendered as a synthetic "not reached" row for the *next* week, since that week never got a job of its own in that run. The table is logged through `loguru` (terminal + `logs/pipeline.log` under the launch scripts) and written verbatim to `logs/runs/{YYYY-MM-DD_HHMMSS}_jobs_run.md` (`JOBS_REPORT_DIR`, `config.py`, default `logs/runs` relative to CWD like `JOBS_DB_PATH`; `logs/` is already gitignored). Any row with a recorded error makes `run` log an error line and `raise typer.Exit(1)`; the Drive push after `_execute` keeps its existing position, unaffected.
- `jobs status` (`cli/commands/jobs.py`) is read-only: the last run's summary (or `--run <id>`), or `--runs` (recent runs with id/started/finished/outcome/failure count via `JobStore.list_runs`), plus a per profile/platform/week overview of current state read straight from the `jobs` table (`jobs/report.py:build_overview_rows`) — story status, plan status, images done/total, schedule status — so it still shows something useful against a DB with no events yet. A `story` job's status (keyed by profile+week only) is attached to every platform row sharing that profile+week rather than getting its own row. `jobs` has no week column, so the overview recovers it by parsing each job id with `jobs/tasks.py:parse_job_id` (`story:{profile}:{week}` has no platform segment at all; `plan`/`schedule` are colon-split; `generate_image` uses the leading path segment); it tolerates the legacy `schedule:{profile}:{platform}` ids (no week segment at all) that predate `schedule_job_id` growing a week dimension, returning `week="unknown"` instead of raising. `cli/main.py:main_callback` special-cases `("jobs", "status")` in `sys.argv` to skip the whole startup preflight (Google Drive pull + profile loading) before it runs, so `jobs status` never touches the network or needs any credentials — safe to run against any `JOBS_DB_PATH` at any time.

## Model Router Behavior
- GitHub Models (the router's original free provider) was fully retired by GitHub on 2026-07-30. `ModelRouter` now routes through an `LLMProvider` abstraction (`apps/ai-content-pipeline/ai_content_pipeline/llm/routing/providers/`) instead of hardcoding any one provider.
- `ModelRouter` tries an ordered list of provider groups: free providers first, then DeepSeek (paid) last as the final fallback. Today the only free provider is OpenRouter (`OPENROUTER_PROVIDER`); DeepSeek and OpenRouter both implement the OpenAI-compatible chat-completions wire format via the shared `OpenAICompatibleProvider` class.
- Adding another free provider is meant to be cheap: a new `LLMProvider` (or `OpenAICompatibleProvider(...)` instance if it's OpenAI-compatible) plus an entry in `ModelRouter`'s `free_providers` list. Do not special-case a new provider's transport/error-handling inside `ModelRouter` or `ModelClassifier` — that logic is provider-agnostic by design.
- Like GitHub Models before it, each profile/account can define its own key — `OPENROUTER_API_KEY_HARU`, `OPENROUTER_API_KEY_CHARLY`, etc. — summed to increase free-tier quota. `ModelRouter` rotates across a provider's keys independently per provider (a cursor per `provider_id`), retrying the next key on quota exhaustion.
- Model discovery is cache-backed and namespaced per provider: `.cache/model_router/{provider_id}_catalog.json`, `{provider_id}_state_{fingerprint}.json` (per API key), `{provider_id}_capabilities.json` (shared across a provider's keys). On the first run without cache, the router fetches a provider's catalog once and reuses it across all of that provider's keys.
- The catalog fetch is metadata only: model IDs, token limits, and similar fields. Do not reintroduce startup probes that send test prompts to every model, because that is slow and consumes quota.
- During generation, the router tries candidate models lazily, highest-ELO first within a provider, and stops as soon as one model returns a usable response. `ModelRouter.last_model` always holds the `(provider_id, identifier)` of whichever model answered most recently; `ModelRouter.exclude_model(provider_id, identifier)` lets a caller stop that one candidate from being offered again for the rest of this router instance's lifetime — in-memory only, never written to the model cache, so the exclusion does not outlive the router (one per `PlanningManager.plan()` call, see Jobs DAG). `ModelRouter.use_fallback_only()` (same instance-only scope) makes every further request go only to the last provider group (the paid fallback), lifting any exclusion on that provider so it always has a candidate. This is how `PlanningManager` (and `StoryManager`, via the same shared `llm/retry.py:generate_with_retries` helper) avoids retrying the exact model that just produced an invalid reply and forces its last attempt onto DeepSeek; it is generic routing behavior, not plan-specific, and keeps `ModelRouter`/`ModelClassifier` provider-agnostic.
- `exclude_model` is a no-op for the paid fallback provider (the last classifier group): excluding it can only make a retry loop worse, since it is the last resort. This matters because every current free OpenRouter model counts as censored for an `is_sensitive_content=True` prompt (arc, chapter, and Fanvue `plan`) — `UNCENSORED_MODEL_GUESSES` (`llm/routing/classification/constants.py`) only matches `"deepseek"`/`"grok"` in the model id, so DeepSeek ends up the *only* candidate for these prompts. Before this fix, one invalid reply got DeepSeek excluded, leaving the next attempt with zero candidates anywhere; `get_response` raised a bare `RuntimeError` that `generate_with_retries` (only catching `ValueError`) did not catch, killing the retry loop on attempt 2 instead of reaching the forced-fallback last attempt. This guard is specifically about `exclude_model`'s behavior, not the censorship heuristic itself — `UNCENSORED_MODEL_GUESSES` is unchanged and still only matches those two names.
- `get_response` raises the dedicated `NoCandidateModelsError` (`llm/error_handlers/exceptions.py`) — not a generic `RuntimeError` — when at least one provider group had a configured API key but every candidate for this prompt was filtered out anyway (excluded, censored, or quota-exhausted with no recovery), so there is no underlying request error to report. The plain `RuntimeError` is reserved for the distinct "no provider has any usable API key at all" case. `llm/retry.py:generate_with_retries` catches `NoCandidateModelsError` alongside `ValueError` and treats it as one more invalid attempt (recorded, retried), so a retry loop that temporarily has zero candidates still reaches its forced-fallback last attempt instead of aborting.
- Runtime failures are learned and cached:
  - Rate limits are stored per provider+API-key fingerprint and skipped until cooldown recovery.
  - JSON-mode requests are validated by actually parsing the reply (via `decode_json_from_message`), not just trusting a 200 response — a model that returns malformed JSON despite `response_format=json_object` (common on free/experimental models) is marked as not supporting JSON and the router fails over to the next candidate, same as an explicit 400. The paid fallback provider is the exception: a malformed JSON reply from it never marks it unsupported, and a cached "no JSON" flag on it is ignored, because it is the last resort (and, for `is_sensitive_content=True` prompts, usually the only candidate); a bad reply just fails that attempt, and the retry loop asks again.
- The cache refreshes automatically after 24 hours. Planning commands can force refresh with `--refresh-model-cache`.
- Prompt files are processed as sequential prompt items, not one persistent API conversation. Continuity comes from local `cache_key` placeholder substitution between prompts.

## Resources And Sync
- Google Drive is used as a simple sync source of truth for managed profile inputs.
- The Drive sync contract covers each profile workflow JSON, each platform's flat `inputs/initial_conditions.md` and `inputs/{profile}.json`, and (both optional, for a profile already migrated to the shared persona/story) `persona.md` and the whole `story/` tree: `story/config.json`, `story/arcs/*.json`, `story/chapters/*.json`. `story/arcs/` and `story/chapters/` must be flat and their file names must be `YYYY-MM-DD.json` (the ISO Monday that arc/chapter starts on) — `GoogleDriveSync` rejects anything else on both pull and push.
- Google Drive push is not append-only. For locally pushed profile folders, `GoogleDriveSync.push()` deletes remote files and folders outside the sync contract, while preserving valid remote profile folders that are not part of the local push.
- Generated images, captions, planning files, publication folders, and other assets under `outputs/` are local runtime artifacts. Do not assume they are committed or synced to Drive.
- `DRIVE_SYNC_ENABLED=false` in the root `.env` turns both directions of the sync into no-ops, guarded inside `GoogleDriveSync.pull()`/`push()` rather than at each call site. Use it when testing a `resources/` layout that is not on Drive yet, so a run can neither overwrite the source of truth nor be overwritten by it. It is per machine: another machine still syncs normally, so pull there before running once the new layout is pushed.
- `GoogleDriveSync.pull()`/`push()` also refuse (clear error) to sync any resources directory other than the repo's default `resources/` (`REPO_ROOT / "resources"`), unless `DRIVE_SYNC_ALLOW_CUSTOM_ROOT=true` is set. This guard is checked after the `DRIVE_SYNC_ENABLED` no-op, so that flag alone still short-circuits silently; the custom-root guard exists so that an `AI_CONTENT_RESOURCES_DIR` pointed at a non-default tree (e.g. a migration sandbox) cannot push to or pull from Drive by accident.
- Do not inspect or modify `resources/` unless the task explicitly requires profile/resource work.
- Do not edit `resources/*/*/inputs/initial_conditions.md`, `resources/*/*/inputs/{profile}.json`, `resources/{profile}/persona.md`, or anything under `resources/{profile}/story/` without explicit user approval. These files define persona/profile setup, prompt behavior, and the generated story (arc/chapter) content.

## Content And Platform Rules
- Meta/Instagram content must be safe for work.
- Fanvue content is adult-oriented and may be explicit. Preserve prompt metadata such as `is_sensitive_content`; the model router uses it to avoid censored models when needed.
- Do not move content expectations between platforms. Meta prompts, captions, and generated assets must stay Instagram-safe; Fanvue-specific explicit content belongs only in Fanvue resources and outputs.
- The Meta publishing integration and standalone Page-token exchange helper target Graph API `v25.0`; keep their versions aligned when upgrading Meta API contracts.
- For Meta/Instagram API behavior, use Meta's official Instagram Postman collection as the most practical agent-friendly source for structured requests, parameters, auth/token flows, publishing examples, and response examples: `https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api`.
- For official Meta/Instagram reference material, use the Instagram Platform docs and API Reference first, then the Graph API overview for concepts: `https://developers.facebook.com/docs/instagram-platform/` and `https://developers.facebook.com/docs/graph-api/overview/`. Meta's `developers.facebook.com/llms.txt` is currently more focused on the Marketing API / Ads MCP surface, so do not treat it as the Instagram-specific source of truth.
- Before changing Instagram auth, token handling, permissions, media container creation, `media_publish`, comments, mentions, insights, Graph API versioning, or Facebook CDN staging, read the current Meta docs and compare them with `apps/ai-content-pipeline/ai_content_pipeline/integrations/meta/graph_api.py`, `apps/ai-content-pipeline/ai_content_pipeline/config.py`, and `apps/ai-content-pipeline/ai_content_pipeline/publishing/posting_scheduler.py`.
- Instagram publishing uses the Instagram API with Facebook Login through `graph.facebook.com`, authenticated with per-profile Facebook Page tokens. Each profile must define `{PROFILE}_INSTAGRAM_ACCOUNT_ID`, `{PROFILE}_FACEBOOK_PAGE_ID`, and `{PROFILE}_FACEBOOK_PAGE_ACCESS_TOKEN`; do not reintroduce profile `INSTAGRAM_USER_ACCESS_TOKEN` publishing through `graph.instagram.com`.
- `all run_all` validates each selected profile's Facebook Page token against its configured Instagram account before clearing outputs or starting planning/generation. Publishing also validates internally before upload.
- To obtain profile Page tokens, generate a Facebook User Access Token for the Business app with `pages_show_list`, `pages_read_engagement`, `instagram_basic`, and `instagram_content_publish`, then prefer the standalone exchange helper at `apps/ai-content-pipeline/scripts/exchange_meta_page_token.py`. The helper is intentionally not a CLI: fill in `GRAPH_API_BASE_URL`, `DEFAULT_PROFILE_ALIAS`, `DEFAULT_PAGE_ID`, and `META_APP_ID` inside the `if __name__ == "__main__"` block, run it directly from PyCharm or with `uv run python apps/ai-content-pipeline/scripts/exchange_meta_page_token.py`, and enter the app secret and short-lived user token only through the hidden prompts. The helper exchanges for a long-lived user token, calls `/me/accounts?fields=name,id,access_token,instagram_business_account`, falls back to direct `/{page_id}?fields=name,id,access_token,instagram_business_account` lookup when the configured Page is not listed, validates the Page's linked Instagram account, and writes `{PROFILE}_FACEBOOK_PAGE_ID`, `{PROFILE}_INSTAGRAM_ACCOUNT_ID`, and `{PROFILE}_FACEBOOK_PAGE_ACCESS_TOKEN` to the repository root `.env` regardless of the process working directory.
- For the full human setup flow covering account email and recovery hardening, Facebook Page creation, Instagram professional account linking, Meta Business Suite, Meta Developer apps, Graph API Explorer permissions, per-Page asset grants when reusing an app across profiles, version caveats, and troubleshooting, use `docs/meta-instagram-page-token-runbook.md`.
- For Fanvue API behavior, use Fanvue's live LLM documentation instead of copying API details into this repo. Start with `https://api.fanvue.com/docs/llms.txt` for the index, and use `https://api.fanvue.com/docs/llms-full.txt` or specific `.md` pages for task details and current request/response contracts.
- Before changing Fanvue auth, media upload, post creation, scheduling, scopes, rate limits, or version headers, read the relevant current Fanvue docs and compare them with `apps/fanvue-fastapi/fanvue_fastapi/`, `shared/fanvue-api-client/fanvue_api_client/`, and `apps/ai-content-pipeline/ai_content_pipeline/integrations/fanvue/`.
- Instagram publishing requires a publicly reachable media URL. This repo intentionally uses `FacebookMediaStager` to upload unpublished photos to the shared Facebook staging Page, read the Facebook CDN URL from the photo `images` payload, and pass that URL to Instagram. This keeps the runtime zero-dollar by avoiding an external storage/CDN service.
- The Facebook staging Page is only a media URL bridge for Instagram. Do not turn it into Facebook cross-posting, do not publish those staging photos, and do not replace this cost-saving flow with paid storage unless the user explicitly asks.
- Instagram Graph API publishing has no native scheduling in this app. Meta scheduling waits asynchronously until each `upload_time`, so running the scheduler can leave the machine sleeping/holding until posts are due.
- `PostingScheduler.upload()` processes every profile in `template_profiles` concurrently (`asyncio.gather` over a per-profile `_upload_profile` coroutine, with one profile's exception logged and isolated from the rest). This applies regardless of caller: `all run_all`, `meta schedule`, and `fanvue schedule` all get concurrent per-profile uploads/scheduling, including Meta's per-profile `_wait_for_time` sleep. Keep new PostingScheduler entry points going through a single instance's `upload()` rather than reintroducing manual per-profile task creation at the call site.
- Fanvue API publishing can pass scheduled `publish_at` timestamps to Fanvue.
- `PostingScheduler._upload_via_fanvue_api` retries a failed publication (media upload + post creation) up to 3 times with linear backoff before giving up and moving to the next day; it does not reuse media UUIDs already uploaded in a failed attempt, so a retry can leave orphaned unused media in the Fanvue vault.
- `httpx` transport-level exceptions (timeouts, connection resets) often have an empty `str()`. Fanvue upload/post error paths (`fanvue_api_client/media.py`, `fanvue_api_client/posts.py`, `posting_scheduler.py`) fall back to the exception type name so failures never log a blank message; keep that fallback when touching these paths.
- `fanvue_api_client/media.py` uses an explicit `UPLOAD_TIMEOUT` (60s) for its `httpx.AsyncClient` calls instead of httpx's 5s default, because multi-megabyte media chunk uploads were hitting spurious `ReadTimeout`s under the default.
- Use ISO 8601 `upload_time` values with an explicit timezone offset, preferably UTC with `Z`. The scheduler accepts `Z` by converting it to `+00:00`; naive datetimes are interpreted using the machine's local timezone and should be avoided.
- Usual operating cadence is weekly: generate a Monday-to-Sunday content batch, keyed by the real ISO date of that Monday (see the Jobs DAG section for `planning_week_start`, history archiving under `outputs/history/`, and the shared arc -> chapter continuity that both platforms' prompts read their week's slice of). Re-running on or after that Monday targets the next Monday-to-Sunday batch, not the week that just finished — the previous week's `{initials}_planning.json` is archived automatically, it is never rewritten in place.

## Safety And Side Effects
- Ask before running commands that touch external services or local generated assets, including Google Drive sync, ComfyUI generation, Meta/Instagram calls, Fanvue API calls, OAuth flows, token validation, uploads, scheduling, or publishing.
- AI content CLI commands such as `uv run python apps/ai-content-pipeline/main.py meta ...` and `uv run python apps/ai-content-pipeline/main.py all ...` load profiles and may pull from Google Drive before executing the requested command.
- Never read, print, commit, or infer secrets from `.env`, token files, OAuth credentials, Instagram access tokens, Fanvue credentials, Google Drive credentials, or generated media/resource outputs.
- Do not modify influencer personas, prompts, profile resources, generated assets, content safety level, or publishing schedules unless the task explicitly asks for it.
- Keep external API interactions mocked in tests unless the user explicitly approves live calls.

## Coding Standards
- Follow the existing Python style and module boundaries. Prefer small, focused changes over broad refactors.
- Use Pydantic models and validators for structured data rather than ad hoc dict or string handling.
- Keep Typer CLI behavior explicit and preserve existing option names unless the task is a CLI migration.
